## Откуда брать макет

Только из **постоянных ссылок** выше либо из ссылок, присланных для конкретной секции.

**Никогда не использовать:**
- текущее выделение в Figma;
- node-id из предыдущих сообщений;
- node-id из памяти прошлых сессий;
- кэш старых секций.

Для каждой новой секции пользователь присылает ссылки именно на эту секцию.

Если хотя бы одна ссылка не открывается через MCP — **остановиться и сказать об этом**.
Не подставлять старые node-id и не достраивать по догадке.

Строго по одному макету за раз, в этом порядке:

## Работа с Desktop-only макетами

Отдельный режим: прислан **только Desktop**, Tablet и Mobile макетов нет.
Это ожидаемая ситуация, а не повод останавливаться.

### Базовый принцип

**Figma desktop — эталон только для desktop.** Всё, что ниже самого широкого
брейкпоинта, — **не макет, а существующее поведение темы, которое нужно сохранить.**

Адаптив в теме уже написан и работает: 38 секций, у каждой своя лесенка из восьми
media-запросов, горизонтального переполнения нет ни на одной из проверенных страниц
ни на одном из вьюпортов 1920 / 1440 / 840 / 392 / 375 (baseline в `docs/QA.md`).
Это рабочая величина, которую легко сломать и трудно восстановить.

### Что делать

1. **Переносить из макета только desktop-значения** — в правила вне media-запросов
   либо в тот брейкпоинт, которому соответствует ширина макета.
2. **Существующие media-запросы секции не трогать**, пока не доказано, что правка
   desktop их сломала. Лесенка остаётся на месте целиком, включая пустые блоки.
3. Если desktop-правка ломает узкие экраны — чинить **точечно, в том брейкпоинте,
   где поломка видна**, а не переписывать весь адаптив секции.
4. **Пропорционально пересчитывать значения вниз нельзя.** Если в макете
   `font-size: 48px` на desktop, из этого не следует `32px` на 768px —
   в теме уже есть своё значение, и оно согласовано с соседними секциями.
5. Новые брейкпоинты не вводить. Список из восьми — закрытый (`docs/FRONTEND.md`).

### Что считать неопределённостью и как её фиксировать

Если из desktop-макета **объективно не выводится** поведение на узких экранах —
не угадывать. Такие места:

- перестроение многоколоночных блоков (во сколько колонок, в каком порядке);
- что скрывается, а что переносится в слайдер;
- поведение декоративных absolute-изображений при сужении контейнера;
- порядок элементов, если на desktop он задан горизонтальной раскладкой.

**Порядок действий:** сохранить текущее поведение темы как есть, а в отчёте по секции
отдельным пунктом перечислить, что осталось неопределённым и какое решение принято
по умолчанию. Накопленные вопросы — в `docs/BACKLOG.md`.

### Ширина макета

Перед первой секцией зафиксировать здесь ширину Desktop-фрейма и то, какому
брейкпоинту темы она соответствует:

| Параметр | Значение |
|---|---|
| Ширина Desktop-фрейма Figma | — |
| Соответствующий брейкпоинт темы | — |
| Ширина контейнера в макете | — |
| Ширина контейнера в теме (`.container`) | — |

Расхождение ширины контейнера — первое, что нужно выяснить: от него зависят
все внутренние отступы секции.

### Проверка после секции

Обязательно на всех пяти вьюпортах, не только на desktop:
**1920 / 1440 / 840 / 392 / 375**.

Сверять с baseline из `docs/QA.md`:
- горизонтального переполнения нет;
- ошибок в консоли не прибавилось;
- 404 не появились;
- высота документа изменилась объяснимо.

Desktop совпал с макетом, а на 375px поехало — **секция не готова.**

### Когда появятся Tablet / Mobile

Заменить этот режим обычным порядком «Desktop → Tablet → Mobile» из раздела выше.
Уже сверстанные по Desktop-only секции **пересмотреть**: то, что сохранялось
как «существующее поведение», может расходиться с присланными макетами.
Список таких секций вести в `docs/BACKLOG.md`.

## Ассеты

### SVG-иконки
Переносить inline, сохраняя геометрию. Подробности и **ловушка обрезанного `viewBox`
в `get_design_context`** — в `docs/FRONTEND.md`, раздел 8. Читать до первого экспорта.

### Растр
Выгружать самому из **чистой ноды изображения / image-fill**, не из скриншота блока:
в композите запечены оверлеи, градиенты, тени и компрессия.

Формат — x1 + x2 WebP (`name.webp` + `name@2x.webp`), x3 не делаем.
Фото q≈82 lossy, логотипы и иконки с альфой — lossless.

**Складывать в `img/` по существующей схеме имён** (`<блок>__<роль>.webp`).
Каталог плоский — новых подпапок без согласования не заводить (`docs/FRONTEND.md`, раздел 9).

Перед выгрузкой — проверить, нет ли такого ассета в проекте.

## Что переносим из макета, а что нет

Ожидаемый объём будущих правок, со слов пользователя: **палитра, изображения
и локальные элементы оформления**. Основные секции остаются.

Поэтому:

- сначала пытаться обновить **существующий токен или существующий модификатор**;
- изменение общего токена требует анализа **всех** мест использования и регрессионной проверки
  — в `styles.css` 384 обращения `var()`, и ни одно из них не объявлено, см. `docs/THEME-TODO.md`;
- структуру секций, `id`, `data-`атрибуты и классы не переделывать под макет без отдельной задачи:
  на них завязаны 31 JS-компонент и якоря навигации.

## Чек-листы после секции

**Pixel check карточек:** одинаковая высота, одинаковое положение кнопок и divider,
одинаковые внутренние отступы, одинаковое расположение контента. Различия — в отчёт.

**Карточки на Mobile:** для каждой карточки сверить по Figma внешний `border-radius`,
внутренние `padding`, размеры отступов, соответствие desktop/tablet/mobile.
**Не переносить значения из предыдущих секций автоматически** — они различаются
даже между карточками одной секции. Особенно внимательно проверять последние
сделанные карточки: в них чаще остаются расхождения.

**Вертикальный ритм:** расстояние до предыдущей и следующей секции,
внутренние вертикальные отступы. Отличия описывать.

**Мини-рефакторинг:** после секции проверить проект на повторяющиеся стили,
компоненты, модификаторы и утилиты. **Код не менять автоматически** —
подготовить отчёт: что объединить, что переиспользовать, что удалить.
Выполнять только после подтверждения.
