## 2026-10-21 — разделение CSS по блокам

### Р-150. Разделение CSS завершено; порядок по реестру; выборочная загрузка отложена

`css/styles.css` (28 619 строк, 3 829 правил) полностью разнесён: `css/base.css`, `css/layout/` (8 файлов), `css/blocks/`
(45 файлов, из них steps/platform/industries — пилот Р-149), `css/pages/` (404, price-matrix). `styles.css` остался
заглушкой и не подключается (удалять без указания нельзя). Перенос без визуальных изменений: сравнение computed styles
до/после на 20 шаблонах × 6–8 ширин (138 кадров, 1,43 млн сравнений; все элементы страницы + открытые модалки) —
0 расхождений на повторной проверке (методика и инструменты — `docs/FRONTEND.md` §2).

Решения по ходу (каждое — чтобы вид не менялся):
1. **Порядок подключения — по реестру `inc/css-registry.php`, плоский список в исходном порядке правил**, а не «base →
   layout → blocks → pages». Подвал, тизер, формы и модалки в исходнике стояли между блоками главной и Solutions; при
   равной специфичности победитель определялся положением.
2. **Общие классы кнопок внутри чужих блоков остались на месте** (`.btn--gray*`/`.btn--small*` в cases, `.btn--black*` в
   doc, `.btn-hero*` в hero, переопределение `.btn*` ≤478.98 в solutions; `.tag` в contacts; `.section__tab*` в benefits):
   в `base` они проигрывали правилам блоков (пример: line-height кнопки «Talk to Sales» 22.5 → 23.94). В `base` ушли
   только `.container` и `.section__title/__subtitle/__badge/__description` из медиа-запросов блоков.
3. **`.modal …`-контексты региона Contacts остались в `blocks/contacts.css`** (`contacts__*` в модальных формах): вынос в
   `layout/modals.css` менял порядок относительно `.contacts__form .input-form-item--50`.
4. **Правило `body.page-template-page-price-matrix .section, body.single-post .section` → `layout/light-content.css`**
   (общее для двух шаблонов; в `base` перебивалось списком teaser). Светлые страницы privacy / price-matrix /
   single-post — `layout/light-content.css` (в шапке файла указано, каким шаблонам служит), не `pages/`.
5. Body-правила страниц и токен-списки — в `base`; токен-список с корнями `.header`, `.modal--form`, `.modal--result`
   режется на base + header + modals. Светлые списки Contacts/Teaser/Footer/FAQ переехали целиком, не менялись.

**Выборочная загрузка стилей блоков (этап 3) — отложена.** Предложение: подключать только блоки текущей страницы
(индекс «класс → файл» + сканирование классов шаблона; `base`/`layout` всегда; фолбэк — все). Отложено владельцем/
координатором: пропуск одного файла ломает страницу на проде, а в CSS остаются (1) общие классы кнопок внутри чужих
блоков, (2) блоки, ждущие универсализации (body-скоуп `idv-*`, `kyc-*`, Home/Solutions-блоки), (3) порядок, зависящий от
положения файла. Сейчас грузится весь реестр на всех страницах (один раз, дальше кэш браузера). Условия возврата —
`docs/BACKLOG.md` → CSS-01.

### Р-149. `css/styles.css` делится по блокам, не по страницам

`css/styles.css` держал вид блоков на body-классах страниц и модификаторах, поэтому блок нельзя было переиспользовать без
страницы-источника. Владелец решил делить файл по БЛОКАМ: каждый блок — свой файл. Пилот (2026-10-21) —
`css/blocks/steps.css`, `platform.css`, `industries.css`; остальное завершено Р-150.

Целевая структура: `css/base.css` · `css/layout/` · `css/blocks/<блок>.css` · `css/pages/<страница>.css` (только
действительно уникальное). Правила: перенос — без визуальных изменений (эталон — computed styles до/после); медиа-запросы
едут вместе со своими правилами, порядок внутри файла сохраняется; групповое правило (`:is(.a, .b)`) разрезается на
правила в файлах блоков; новый блок — свой файл в `css/blocks/`, стили блока не зависят от страницы. Снимает пункт
«Новых CSS-файлов не заводим» из `docs/FRONTEND.md` для `css/base.css`, `css/layout/`, `css/blocks/`, `css/pages/`;
остальные запреты `CLAUDE.md` (новые каталоги ассетов, брейкпоинты, рефакторинг вне блока) действуют.

## 2026-10-20 — страницы из блоков библиотеки

### Р-148. Новая страница — один шаблон `page-<slug>.php` с «семейством оформления»

Владелец заказал агента, который собирает новые страницы из готовых блоков по ТЗ; страницы
заливаются на прод файлами, шаблон выбирается в админке. Оформление блоков привязано к body-классу
шаблона-источника (Identity ≈640 правил, KYC ≈386, Solutions ≈384: вид блоков, светлые шапка /
подвал / Contacts / FAQ, контракт `--nv-block-space`), поэтому новый шаблон сам по себе получил бы
голые блоки.

Решено: шаблон объявляет `NV Page Family: identity | kyc | solutions` в шапке файла;
`inc/page-builder.php` добавляет странице body-класс шаблона-источника и включает
`nv_is_light_theme()`. CSS не копируется и не переписывается; регистрировать новый шаблон
в списках не нужно. Рефакторинг селекторов `body.page-template-*` в модификаторы — отдельная
задача, не делается. Блоки главной (`body.home`) для сборки недоступны.

Предпросмотр без записи в БД: `?nv_page_preview=page-<slug>.php` на любой обычной странице
(не главной), только администратору, остальным 404, `noindex`. Подменяется `_wp_page_template`
запрошенной страницы через `get_post_metadata`, поэтому `is_page_template()` и body-классы
ведут себя как у настоящей страницы.

Регламент агента — `docs/PAGE_BUILDER.md`; память по странице — `docs/pages/<slug>.md`.

## 2026-10-14 — доработка страницы записи блога и блоков

### Р-142. Комментарии по макету 2570:39540 — включаются на записи, прежняя форма остаётся запасной

  форма анонимная и без капчи; модераторы и спам-статус не затронуты;
- после отправки — возврат на форму с уведомлением «awaiting moderation»;
- даты выводятся по-английски независимо от локали WP (она `ru_RU`).

## 2026-10-13 — редактирование полей ACF-блоков

### Р-139. Стили ACF отдаются в iframe-канву через `editor_style_handles`
Канва редактора WordPress 7 — отдельный iframe; ACF печатает форму полей внутрь
неё, а стили подключает только в родительский документ. Поэтому после
`register_block_type()` каждому блоку дописываются хэндлы `acf-input`,
`editor-buttons` и `buttons`: ядро кладёт `editor_style_handles` всех блоков
в iframe (`_wp_get_iframed_editor_assets()`).

Инлайнить CSS в настройки редактора не стали: хэндлы подключаются ссылкой
и кэшируются, а зависимости (`acf-global`, `dashicons`) ядро разрешает само.

### Р-140. Блоки с WYSIWYG верхнего уровня — в режиме `preview`
TinyMCE инициализируется в родительском документе и до textarea внутри iframe
не дотягивается: в канве у WYSIWYG-поля нет панели инструментов. В режиме
`preview` ACF печатает поля в правую панель блока — это родительский документ,
и визуальный редактор там работает.

Переведены с `auto` на `preview`: `spoiler`, `note`, `warning`, `success`,
`disclaimer`, `quote`, `result`, `about`. Уже были в `preview`: `callout`, `toc`.

Блоки с репитерами остаются в `auto`: репитер в панели шириной ~250
сжимается в нечитаемую таблицу (проверено на `tabs`), а в канве форма шире.
Их WYSIWYG-подполя остаются без панели инструментов — вкладка «Текст» работает.
**Открытый вопрос:** перевести эти подполя (`steps_text`, `tab_text`,
`slider_title`, `gallery_image_caption`) в настройках ACF на «Только текст» —
тогда они станут обычной textarea и заработают в канве полноценно.

Снять оба решения можно после обновления ACF Pro до версии с поддержкой
iframe-канвы (`docs/BACKLOG.md`, B-27).

## 2026-10-12 — Белая стрелка в кнопке шапки

### Р-121. Цвет lottie-стрелки задаётся через `currentColor`, а не `fill`
Стрелку в `.btn--header` рисует lottie из `arrow_right_black.json`.
Цвет там задан **атрибутом `stroke="rgb(0,0,0)"` прямо на путях**,
а заливки у них нет вовсе (`fill-opacity="0"`). Правило, добавленное
для Solutions раньше, красило только `fill` — поэтому стрелка оставалась
чёрной, хотя подпись кнопки белая.

теперь ведём через `currentColor` кнопки: он красит и пути lottie
(`stroke`), и запасную inline-иконку (`fill`), которая видна до

## 2026-10-12 — Solutions, Why: нахлёст карточек и фотография под ними

### Р-119. Нахлёст карточек — 400, как в макете
В `2456:16533` у каждой карточки `margin-right: -400`: следующая уходит
под неё целиком, вместе со своими левыми скруглениями. Видна только
прямая кромка предыдущей карточки.

В вёрстке нахлёст был 24 — ровно радиус скругления, поэтому левый угол
каждой полоски упирался в правый угол соседа и на стыке читалась выемка.
`--swhy-tuck` переведён с 24 на 400.

Ширины при этом не изменились: ширина карточки считается как
«видимая часть + нахлёст», а положение содержимого внутри карточки
от нахлёста не зависит вовсе — контент прижат к правому краю, и его
смещение относительно видимой кромки равно `--swhy-card-open − 23 − 468`
при любом нахлёсте. Проверено: 516 / 116 / 116 / 116 на 1920 и 1440,
переключение на третью карточку даёт 116 / 116 / 516 / 116.

### Р-120. Фотография заходит под карточки
В макете фотография — фон всего блока `2456:16531` (`inset: 0`), карточки
лежат поверх. У нас это была отдельная колонка встык с карточками,
поэтому скруглённый правый угол последней карточки открывал подложку
доски, а не фотографию, и слева у снимка читался прямой обрыв.

Блок карточек получил `margin-right: -112` — ровно как `2456:16532`
в макете. Фотография начинается на 112 левее и уходит под карточки.

**Побочный эффект:** на 1600 и выше ассет `sol-why-fhd.webp` вырезан
ровно под прежнее поле 992, а теперь поле 1102, поэтому снимок
отрисовывается примерно на 11% крупнее. На 1440 и ниже ассеты шире
поля — там масштаб только уменьшается. Если крупнее не годится, нужен
ассет на 112 шире либо уменьшение нахлёста до 40 — этого хватает,
чтобы угол карточки открывал фотографию. Вынесено в BACKLOG A-52.

На планшете и мобильной доска становится колонкой: там нахлёст и
смещение фотографии сняты.

## 2026-10-12 — Светлый редизайн всплывающих форм

### Р-113. Токены светлой темы объявлены и на модалках

### Р-114. Оформление полей переиспользовано, а не продублировано
Разметка модалок использует тот же словарь классов, что и общая форма:
`.input-form-item`, `.input-form-block`, `.input-form-label`, `.phone-field*`,

от объединения не окупает риск, а визуального дублирования и так нет:
стили общие.

### Р-115. Модификаторы вместо скоупа по body
Светлый дизайн не должен зависеть от страницы, но и не должен задевать
окно отзывов `#review`, которое остаётся тёмным. Поэтому на модалки

(`#thanks`, `#error`). Все новые правила опираются на них.

Кнопки закрытия в макетах нет ни в одном фрейме, но окно обязано
закрываться не только Escape и кликом по подложке. Взяли оформление
кнопок очистки из той же системы: 28x28, рамка Stroke 2, скругление 6,
в поле окна справа сверху.

### Р-116. Окна результата на мобильной — в столбик
Для `#thanks` и `#error` мобильного фрейма в макете нет. Маскот 294px
рядом с текстом в 360 не помещается и перекрывает его, поэтому ниже

### Р-117. Светлые выпадающие списки — пока только в модалках

### Р-118. Окно результата открывается в следующем кадре
`MicroModal.close()` возвращает фокус на триггер формы уже после того,
как `show()` увёл его в диалог результата. Из-за этого фокус уходил
из окна. Теперь закрытие формы и открытие результата разнесены через
`requestAnimationFrame`, а в `onShow` фокус ставится на кнопку закрытия.

### Вертикальное пространство контентных блоков — 2026-10-19

На текущих шаблонах Home, Solutions, KYC, Identity и Pricing Matrix каждый контентный блок после первого экрана
