# Правила работы

Всегда отвечай на русском языке.

## Общие правила

При работе с проектом:

* Все объяснения, отчёты, планы работ и комментарии писать на русском языке.
* Код писать без перевода.
* Названия файлов не переводить.
* CSS-классы и HTML-атрибуты не переводить.
* Перед внесением изменений кратко объяснять план действий.
* После завершения работы показывать список изменённых файлов.
* Не выполнять масштабный рефакторинг без явного указания.
* Не изменять структуру проекта без необходимости.
* Предпочитать минимально необходимые изменения существующего кода.

## Работа с Figma

При разработке страницы всегда использовать **только постоянные ссылки** на Desktop, Tablet и Mobile макеты, сохранённые в `PROJECT_STATE.md` (раздел «Figma — постоянные ссылки»).

**Никогда не использовать:**

* текущее выделение Figma;
* node-id из предыдущих сообщений;
* node-id из памяти предыдущих сессий;
* кэш старых секций.

Для каждой новой секции пользователь присылает ссылки именно на эту секцию (Desktop / Tablet / Mobile).

**Алгоритм работы:**

1. Открыть Desktop-ссылку секции.
2. Получить Screenshot.
3. Получить Design Context.
4. Получить Metadata.

Затем то же самое для **Tablet**, затем для **Mobile**.

Только после анализа всех трёх версий приступать к: анализу компонентов → анализу ассетов → экспорту ассетов → вёрстке → pixel-check → typography-check.

Если хотя бы одна ссылка недоступна / не открывается через MCP — **сразу остановиться и сообщить пользователю**. Не пытаться использовать старые node-id или данные предыдущих секций.

Три базовые ссылки в `PROJECT_STATE.md` — постоянная основа проекта; использовать их, пока пользователь явно не заменит.

### Типографика

* Для текстовых элементов **не использовать `line-height` в пикселях**.
* Использовать относительные значения: проценты (`120%`, `140%`, …) — **предпочтительно** — либо множитель (`1.2`, `1.4`).
* Расчёт из макета: `line-height ÷ font-size × 100`, округление до 2 знаков при необходимости.
  * Пример: `font-size: 40px; line-height: 48px;` → `font-size: 40px; line-height: 120%;`
* `font-size` оставлять в пикселях (по макету).

#### Неразрывный пробел (`&nbsp;`) при переносе текстов из Figma

Чтобы короткие слова и знаки не «повисали» в конце строки, при переносе видимого текста (заголовки, подзаголовки, описания, кнопки) ставить `&nbsp;` вместо обычного пробела:

1. **После предлогов и союзов** — приклеивать к следующему слову. Пример: `для&nbsp;приложений`, `на&nbsp;сайте`, `с&nbsp;картой`.
2. **Частицы `бы, же, ли, ль`** — приклеивать к предыдущему слову: `если&nbsp;бы`, `так&nbsp;же`.
3. **Числа** — между числом и словом/единицей и в разрядах: `200&nbsp;стран`, `5&nbsp;лет`, `10&nbsp;000`, `№&nbsp;5`, `30&nbsp;%`. Дефисные — через дефис без пробела (`152-ФЗ`).
4. **Сокращения и инициалы**: `и&nbsp;т.&nbsp;д.`, `т.&nbsp;е.`, `г.&nbsp;Москва`, `И.&nbsp;И.&nbsp;Иванов`.

**Предлоги** (приклеивать к следующему слову):
* 1 буква: `в, к, о, с, у`
* 2 буквы: `во, ко, со, об, от, из, по, до, за, на, над, под`
* 3 буквы: `обо, ото, изо, при, про, без, для, близ`

**Короткие союзы** (тоже к следующему слову): `и, а, но, да, или`.
**Длинные предлоги** (перед, через, около, между, среди, кроме, после, вдоль, вокруг, против, сквозь, ради, из-за, из-под) — по ситуации, только если реально «повисают».

Не злоупотреблять: склеивать только короткие слова; в узких мобильных колонках длинные склейки дают большие пробелы — проверять.

### Раскладка (Flexbox)

* Основной инструмент построения макетов — **Flexbox** (`display: flex` + `flex-direction`, `justify-content`, `align-items`, `flex-wrap`, `gap`, `flex-grow/shrink/basis`).
* **CSS Grid по возможности не использовать.** При выборе между Grid и Flex — всегда Flexbox.
* Горизонтальные ряды, карточки, колонки, адаптивные перестроения и Swiper — строить только через Flexbox.
* Сетки карточек — `flex-wrap: wrap` + ширина элемента, напр. `flex: 0 0 calc((100% - 32px) / 3)`.
* **Не использовать Grid** для секций Hero, Cards, Features, Products, Logos, Testimonials, Blog, Footer.
* Grid допустим только в исключительных случаях, когда Flexbox объективно усложняет код — **сначала объяснить причину и получить подтверждение**.

### Кнопки

* **Не использовать `height`** для текстовых кнопок — использовать **`min-height`**.
* Кнопка должна иметь возможность увеличиваться по высоте при переносе текста / других языках.
* Размеры по макету достигаются через `box-sizing: border-box` (border входит в итоговый размер), а не фиксированной высотой.
* Фиксированная `height`/`width` допустима только для **иконок-кнопок** (квадратных): 40×40, 56×56 и подобных.

### Декоративные absolute-изображения

При использовании `position: absolute` для декоративных изображений:

* **Заранее резервировать место** под изображение в блоке (`padding-right` / `padding-bottom` и т.п.), исходя из **проанализированной ширины/высоты изображения и его смещения** (например `padding-right = смещение справа + ширина изображения`). Значения не «магические» — выводятся из макета и комментируются.
* Текст, кнопки и прочий контент **никогда** не должны попадать под absolute-изображения.
* **Проверять промежуточные ширины** экранов (не только контрольные точки макета) — особенно диапазоны между брейкпоинтами, где контейнер сужается.
* Если изображение по макету **выходит за пределы блока** — использовать **смещение** (`top`/`right`/…) и **`overflow: hidden` на контейнере изображения**, а не менять размеры самого изображения. Кадрирование делать контейнером/`object-fit`, не масштабированием картинки.
* Если нужно одновременно «выступать сверху» и «обрезаться снизу границей блока» — обернуть изображение в контейнер, растянутый `top`/`bottom` (он тянется по высоте блока + выступ), с `overflow: hidden`; сам блок — `overflow: visible`. (`<img>` — replaced-элемент, его нельзя растянуть парой `top`+`bottom`.)

### UI SVG-иконки

Все небольшие интерфейсные SVG-иконки вставлять **непосредственно в HTML как inline `<svg>`** (стрелки, chevron, plus/minus, check, крестики, search, burger, play/pause, download, calendar, соц-/контакт-иконки и т.п.).

* Использовать `fill="currentColor"` (или `stroke="currentColor"`) — цвет управляется **только через CSS** (`color` элемента/родителя).
* Анимации (поворот, масштаб, прозрачность) выполнять **через CSS** (`transform`, `opacity` на самом `<svg>`), а не сменой файла.
* Размер задавать через CSS-класс на `<svg>` (`width`/`height`); `viewBox` сохранять для пропорций.
* Добавлять `aria-hidden="true"` и `focusable="false"` для декоративных иконок.

**Не использовать `<img src="icon.svg">` для интерфейсных элементов.**

`<img>` применять только для: логотипов компаний; фотографий; декоративных SVG; сложных иллюстраций; самостоятельных графических объектов (напр. `logo.svg`, фоновые иллюстрации, указатель шкалы с фильтром-тенью).

**Перед добавлением новой иконки — проверить проект.** Если такая SVG уже используется — переиспользовать **точно тот же** SVG-код (одинаковый `viewBox` + `path`), не создавать дубликат-вариант. (Пример общего кода: chevron в навигации `.nav__arrow` и в кнопке `.clients__more-icon`.)

#### Перенос SVG-иконок из Figma

При переносе inline SVG из Figma **запрещено оптимизировать SVG так, чтобы менялась исходная геометрия иконки.**

Обязательно сохранять:

* исходный `viewBox`;
* исходные размеры `width` / `height`;
* исходные координаты `path d`;
* внутренние отступы внутри `viewBox` (пустые поля иконки);
* `clipPath` / `mask` / `defs`, если они влияют на отображение.

Запрещено:

* пересчитывать `viewBox` по фактическим границам path;
* обрезать пустые поля внутри SVG;
* масштабировать path вручную;
* менять координаты `path d`;
* переносить иконку в другой `viewBox` (если в макете она была `24×24` — оставить `24×24`).

Разрешено:

* заменить фиксированный `fill`/`stroke` на `currentColor` для управления цветом через CSS;
* удалить `clipPath`/`defs` **только** если визуально ничего не меняется и это проверено (напр. `clipPath` = `<rect>` на весь `viewBox`);
* сделать `id` внутри `defs` уникальными, если иконка повторяется на странице несколько раз (иначе — дубли `id` в DOM).

После переноса — **сравнить иконку с макетом Figma**: она должна занимать то же положение внутри `viewBox`, а не просто «выглядеть похоже».

##### ⚠️ Ловушка MCP (`get_design_context`) — обрезанный `viewBox`

`get_design_context` (Figma MCP) при выгрузке иконок часто отдаёт **обрезанный** SVG: отдельный `<path>` с `viewBox` по границам самого path (напр. стрелка приходит как `viewBox="0 0 5.92858 10.6667"` — без внутренних полей), вместо исходного **квадратного кадра иконки** (`24×24` с отступами). Если вставить такой обрезанный вариант в слот заданного размера (напр. `.btn__icon` в `.btn--xl` = 24×24), иконка растягивается «от края до края» и **не совпадает с макетом** (в макете тот же глиф занимает ~2/3 кадра, с полями). Именно из-за этого стрелки в мобильном меню («Продукты», CTA) приходилось переисправлять.

Правило:

* **Не копировать `viewBox` из codegen-вывода MCP вслепую.** Для иконки брать её **родной кадр** (обычно квадрат — `24×24`, `16×16`), а внутри него — path с исходными полями.
* Если MCP отдал только обрезанный path — считать это неполной выгрузкой: взять `viewBox` иконки-компонента (её frame в Figma), либо запросить у пользователя корректный экспорт, либо восстановить квадратный `viewBox` с теми же внутренними отступами (не растягивать глиф на весь кадр).
* Признак проблемы: `viewBox` не квадратный / подозрительно «тесный» (равен габаритам глифа) — почти всегда это обрезка codegen, а не настоящий кадр иконки.
* После вставки — **проверить в браузере**, что видимый глиф занимает ту же долю кадра, что в макете (есть внутренние поля), а не заполняет слот целиком.

### Растровые изображения (фото / иллюстрации) — выгрузка из макета

Растровые изображения из макета (фото, иллюстрации, декоративные картинки) **выгружать самому** — это шаг «экспорт ассетов» пайплайна, а не повод просить файл у пользователя. Просить — только когда источник объективно недоступен (см. ниже).

**Источник — чистая нода изображения, а не скриншот блока.** Брать изображение из **отдельного слоя/image-fill** в Figma. **Нельзя** вырезать картинку из композитного скриншота секции: в нём запечены оверлеи, градиенты, тень и рамка карточки, плюс компрессия (напр. тёмная CTA-плашка `.testimonials__cta` лежит поверх фото — из такого скрина чистого ассета не получить).

**Как получить (по приоритету):**

1. **Figma MCP доступен** — выгрузить ноду конкретного слоя-изображения (`download_assets` / image-fill) по node-id из постоянных/присланных ссылок секции (правила «Работа с Figma»).
2. **MCP недоступен (View-seat) или нода не отдаётся** — запросить у пользователя экспорт **именно этого слоя** в исходном разрешении (указать node-id / имя слоя). Композит блока не подходит — сказать об этом явно.

**Формат, имена, папка** (из `docs/TOKENS.md` → «Ассеты»):

* Растр — только **x1 + x2**: `name.webp` + `name@2x.webp` (x3 не создаём). Пиксельный размер x1 = размер слота по макету, `@2x` — вдвое.
* Фото/иллюстрации — **WebP lossy q≈82**; логотипы и иконки с альфой — **WebP lossless**.
* Класть в `img/<секция>/` (напр. `img/testimonials/`). Исходники из Figma — в `img/source/` (в вёрстке не используются).
* В `<img>`: `srcset="...webp 1x, ...@2x.webp 2x"` + явные `width`/`height` (пиксельный размер слота — без скачка layout) + осмысленный `alt` (для чисто декоративных — `alt="" aria-hidden="true"`).

**Размер и кадрирование.** Экспортировать под фактический слот макета (с учётом `object-fit: cover` — картинка должна покрывать слот). Кадрирует и позиционирует **CSS-контейнер** (`object-position`, `overflow`), саму картинку вручную не масштабировать — см. «Декоративные absolute-изображения».

**Перед выгрузкой** — проверить, нет ли уже такого ассета в проекте (не плодить дубли).

**Если правильного ассета пока нет** — не выдавать чужой/заглушечный файл за финальный молча: пометить `src` как placeholder и вынести вопрос пользователю, но геометрию слота (размеры, %, `object-position`) выставить по макету, чтобы корректный файл встал без переверстки.

### Доступность интерактивных компонентов

Все интерактивные компоненты делать **семантически правильно и доступно** (ARIA + клавиатура).

Для **Tabs** обязательно:

* `role="tablist"`, `role="tab"`, `role="tabpanel"`;
* `aria-selected` на вкладках;
* `aria-controls` (вкладка → панель) и `aria-labelledby` (панель → вкладка);
* `hidden` на неактивных панелях;
* **roving tabindex** (активная вкладка `tabindex="0"`, остальные `-1`);
* клавиатурная навигация: стрелки (←↑→↓), `Home`, `End`.

Аналогичный подход (нужные ARIA-роли/атрибуты + клавиатура + фокус) применять к другим интерактивным паттернам (аккордеоны, модалки, дропдауны, слайдеры).

### Состояние карточек (flip / переключение)

**Не использовать `:hover` как единственный способ управления состоянием карточек.** Состояние переключать через CSS-класс (например, `.is-flipped`), который добавляет/убирает JavaScript:

* **Desktop** (есть hover — `@media (hover: hover)` / `matchMedia('(hover: hover)')`) — переключать по `mouseenter` / `mouseleave`.
* **Планшеты и мобильные** (без hover — `(hover: none)`) — переключать по `click` (toggle).

Ключ — **наличие hover**, а не ширина экрана и **не** `pointer: fine` (последнее отсекает сенсорные/гибридные desktop-устройства).

Это даёт единое поведение на всех устройствах (на touch чистый `:hover` «залипает» и недоступен) и упрощает развитие компонента. Визуальные стили состояния вешать на класс (`.is-flipped`), а не на `:hover`. Реализация — общий помощник в `js/main.js` (элементы с атрибутом `data-flip`). Простую подсветку кнопок/ссылок (цвет/фон) можно оставлять на CSS `:hover` — правило касается именно **состояния карточек**.

## Разработка, переиспользование и проверки

### 1. Переиспользование компонентов
Перед созданием нового компонента — анализировать существующие. Если новый элемент отличается только **размерами / цветом / внутренними отступами / типографикой / мелкими визуальными параметрами** — расширять существующий компонент через **модификатор**. Новый компонент создавать только при отличии **структуры, логики или назначения**.

### 2. Новые модификаторы
Любой новый модификатор (`.btn--sm`, `.btn--xl`, `.card--…`, `.hero--…` и т.п.) — сначала обосновать: проверить существующие → объяснить, почему не подходят → только потом создавать. Если существующий подходит — новый не создавать.

### 3. SVG и изображения
Перед экспортом/созданием новой SVG-иконки — проверить проект. Если иконка уже есть — использовать существующую. **Не создавать дубликаты SVG.**

### 4. Pixel Check карточек
Дополнительно проверять: одинаковую высоту карточек; одинаковое положение кнопок; одинаковое положение divider; одинаковые внутренние отступы; одинаковое расположение контента внутри карточек. Различия — фиксировать в отчёте.

#### Проверка карточек на Mobile
После завершения каждой новой секции **обязательно дополнительно проверять мобильную версию всех карточек**. Для каждой карточки сверять через Figma MCP:

* внешний `border-radius`;
* внутренние `padding`;
* размеры внутренних отступов;
* соответствие desktop / tablet / mobile-токенам.

**Не использовать автоматически значения из предыдущих секций.** Даже если большинство карточек проекта имеют одинаковые параметры, каждый раз проверять конкретную карточку текущей секции по макету Figma (значения могут отличаться даже между карточками одной секции — напр. разный вертикальный `padding`).

Особенно внимательно проверять **последние** реализованные карточки перед завершением секции — именно в них чаще остаются мелкие расхождения. Секцию считать полностью завершённой только после проверки этих параметров.

### 5. Вертикальный ритм
После каждой секции проверять: расстояние до предыдущей и следующей секции; соответствие вертикального ритма макету; совпадение внутренних вертикальных отступов. Отличия — описывать.

### 6. Проверка дизайн-системы
Перед созданием нового цвета / радиуса / размера шрифта / размера кнопки / divider / карточки / shadow / spacing — проверить, нет ли уже такого в проекте. Если есть — использовать существующее. Не создавать новые значения без необходимости.

### 7. Мини-рефакторинг после каждой секции
После каждой секции анализировать проект на повторяющиеся стили / компоненты / модификаторы / переменные / утилиты. Код **не менять автоматически** — подготовить отчёт: что объединить, что переиспользовать, что удалить, что оставить. Рефакторинг — только после подтверждения пользователя.

## Git и синхронизация с GitHub

* Статика (`html/`) под git; remote `origin` — `git@github.com:matveevds/neurovision-html.git` (SSH, ключ пользователя).
* Правки пользователя отслеживаются через `git diff` **по его команде** («синхронизируй» / «что я наменял?»): раскладываю их в `WP-SYNC.md` (точечный CSS → «Журнал микро-правок» `MICRO-NNNN`; структурное/логическое/многофайловое → `SYNC-NNNN`) и коммичу. Свои и пользовательские правки коммичу отдельными коммитами.
* **Пуш — НЕ после каждого коммита.** Пушить в `origin` только **раз в конце дня** либо по **прямому указанию** пользователя. Коммитить можно свободно; публикация (push) — по расписанию/команде.
